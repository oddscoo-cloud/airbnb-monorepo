# Документация фронтенда HomeFU

Фронтенд HomeFU — одностраничное приложение на React 19 и TypeScript. Vite собирает клиент, Tailwind CSS подключён как Vite-плагин, а интерфейс взаимодействует с ASP.NET Core API через относительные URL `/api/...`.

Инструкция по запуску всей системы, Docker, базе данных и настройке backend находится в [корневом README](../README.md). Здесь описаны структура, поведение и разработка именно фронтенда.

## Быстрый старт

Нужны Node.js и npm. Для работы интерфейса с данными отдельно запустите backend на `http://localhost:5189`; полный вариант запуска описан в [корневом README](../README.md).

Из каталога `frontend/`:

```sh
npm ci
npm run dev
```

Vite запустит dev-сервер (обычно `http://localhost:5173`). Для локальной разработки он проксирует на `http://localhost:5189` запросы к `/api`, `/listing-images` и `/avatars`.

Чтобы включить вход Google, скопируйте `frontend/.env.example` в `frontend/.env` и задайте `VITE_GOOGLE_CLIENT_ID`. Без этой переменной остальные экраны доступны, но Google OAuth не настроен. Vite читает переменные при запуске dev-сервера; для production значение встраивается в сборку.

Команды:

| Команда | Назначение |
|---|---|
| `npm run dev` | Dev-сервер Vite |
| `npm run build` | Проверка TypeScript (`tsc -b`) и production-сборка в `dist/` |
| `npm run preview` | Локальный просмотр production-сборки |
| `npm test` | Однократный запуск Vitest |
| `npm run lint` | Проверка Oxlint |

## Архитектура и структура

```text
frontend/
├── index.html                 # HTML-точка входа и внешние шрифты
├── vite.config.ts             # React, Tailwind и proxy API/медиа
├── package.json               # Скрипты и зависимости
└── src/
    ├── main.tsx               # React root, OAuth, язык и Suspense
    ├── App.tsx                # Состояние приложения и переключение экранов
    ├── api/                   # HTTP-клиент и клиенты ресурсов backend
    ├── components/            # UI, сгруппированный по функциям
    ├── hooks/                 # Состояние, связанное с API и аккаунтом
    ├── types/listing.ts       # Общая UI-модель объявления
    ├── utils/                 # Переиспользуемые чистые функции
    ├── i18n.tsx               # Контекст украинского и английского языков
    ├── tokens.css             # Цвета, типографика, отступы и радиусы
    ├── index.css              # Глобальные стили и импорты CSS
    └── App.css                # Стили приложения
```

Маршрутизатора в проекте нет: `App.tsx` хранит текущий экран в React state и передаёт дочерним экранам callback-функции навигации. Переход на экран не меняет URL; обновление страницы возвращает начальное состояние приложения. Диалоги входа и регистрации реализованы через portal.

`main.tsx` оборачивает приложение в `StrictMode`, `GoogleOAuthProvider`, `LanguageProvider` и общий `Suspense` с экраном загрузки. Основные страницы и карты загружаются через `React.lazy`; Leaflet не требуется в начальной загрузке каталога.

### Поиск и каталог

Состояние поисковых фильтров принадлежит `App`. Каталог загружает регионы отдельно от списка объявлений. Ввод фильтра запускает загрузку с задержкой 250 мс; запросы отменяются при смене фильтра или размонтировании компонента. Кнопка поиска повторно запрашивает каталог. Запрос объявлений проходит по страницам размером 100 записей до получения неполной страницы.

Фильтры API: `region`, `category`, `minPrice`, `maxPrice`, `minimumRating`, `guests`, `checkIn`, `checkOut`. Даты передаются как `YYYY-MM-DD`. Смена региона доступна как в основной форме, так и в навигации категорий. Кнопка сброса очищает регион, даты, цену, рейтинг, категорию и число гостей.

Избранное требует авторизации. После входа список ID и полные объявления загружаются параллельно; переключение сердечка сначала оптимистично обновляет интерфейс, а при ошибке откатывает изменение и отображает ошибку.

## Состояние и переходы

Основное состояние приложения находится в `App.tsx`:

- `activePage` — один из экранов `home`, `listing`, `booking`, `payment`, `admin`, `profile`, `account`, `verification`, `host`;
- `selectedListing`, даты поездки и вариант оплаты — данные текущего сценария объявления;
- фильтры и число гостей — состояние поиска каталога;
- модальные окна и карта — отдельные флаги отображения;
- `listingsRevision` — сигнал повторной загрузки каталога после изменений.

Без выбранных дат длительность поездки в интерфейсе бронирования по умолчанию равна пяти ночам. При возвращении в каталог выбранное объявление и даты сбрасываются. Профиль, аккаунт и административные экраны доступны как внутренние состояния приложения, а не как прямые URL.

Сессионные данные браузера:

| Ключ | Хранилище | Назначение |
|---|---|---|
| `access_token` | `sessionStorage` | Access token для авторизованных запросов, живёт в рамках вкладки |
| `account_email`, `account_role` | `sessionStorage` | Отображение аккаунта и роли |
| `account_avatar` | `sessionStorage` | Кэш URL аватара между компонентами в текущей вкладке |
| `homefu-language` | `localStorage` | Выбранный язык между запусками браузера |

Refresh token обрабатывается через cookie и endpoint обновления сессии. Выход очищает клиентские данные сессии. Не используйте браузерное хранилище как источник авторизации на backend: API должен проверять токен независимо.

## Работа с API

### HTTP-клиент

Для новых API-интеграций используйте `apiRequest<T>` из `src/api/http.ts` вместо прямого `fetch`, если нет специфичной причины поступить иначе. Клиент:

1. Добавляет `Authorization: Bearer ...`, если передан `accessToken`.
2. Устанавливает JSON `Content-Type` для обычного тела запроса; не задаёт его для `FormData`, чтобы браузер сформировал `boundary`.
3. При `401` авторизованного запроса один раз обращается к `/api/auth/refresh` с cookie и повторяет запрос, если получен новый токен.
4. Разбирает JSON-ответ; для `204` возвращает пустое значение. Некорректный JSON успешного ответа приводит к ошибке.
5. Для HTTP-ошибки использует поле `message` ответа, затем переданный `fallbackError`, иначе текст `Request failed (<status>)`.

Ответ типизируется generic-параметром на стороне TypeScript, но клиент не проверяет его структуру во время выполнения. Для файлов используйте `FormData`; для JSON — `JSON.stringify`.

### Используемые endpoint-группы

| Функция | Endpoint |
|---|---|
| Сессия | `POST /api/auth/register`, `/login`, `/google`, `/refresh`, `/logout`; `GET /api/auth/me` |
| Каталог | `GET /api/listings` (параметры фильтров, `page`, `pageSize=100`); `GET /api/listings/regions` |
| Вопрос по объявлению | `POST /api/listings/{id}/questions` |
| Пользователь | `GET /api/users/{id}`; `PUT /api/users/me/facts`; `POST /api/users/me/avatar`; `POST /api/users/me/verification` |
| Сохранённые | `GET /api/saved-listings`, `GET /api/saved-listings/ids`; `POST` и `DELETE /api/saved-listings/{id}` |
| Регионы | `GET /api/region`, `GET /api/region/all` |
| Объявление хозяина | `GET /api/host/listings/amenities`, `POST /api/host/listings/amenities`, `GET /api/host/listings/mine`, `POST /api/host/listings` |
| Объявления в админке | `GET` и `POST /api/admin/listings`; `PUT /api/admin/listings/{id}`; `POST /api/admin/listings/{id}/publish`; `POST /api/admin/listings/{id}/images`; `DELETE /api/admin/listings/{id}/images/{imageId}` |
| Заявки хозяев | `GET /api/admin/submissions?status=...`; `PUT /api/admin/submissions/{id}`; `POST /api/admin/submissions/{id}/approve`; `POST /api/admin/submissions/{id}/reject` |

Реализация endpoint-клиентов размещается в `src/api/`; экран отвечает за UI-состояние, ошибки и пользовательские действия. Большинство API-вызовов принимают `AbortSignal`, чтобы отменить загрузку при уходе с экрана.

## Модели данных

`ListingResponse` — DTO backend. `mapListingResponse` преобразует его в UI-модель `Listing` из `src/types/listing.ts`: `pricePerNight` становится `price`, `longtitude` остаётся именем координаты API, а обложка сортируется перед остальными изображениями. Если сервер не прислал изображения, выбирается детерминированный набор локальных резервных путей `/listing-photos/fallback-*.webp`.

Общая UI-модель `Listing` включает:

- идентификатор, название, описание, локацию, регион и категорию;
- цену за ночь, рейтинг, количество отзывов и допустимое число гостей;
- удобства и отзывы;
- статус публикации, основное изображение и галерею;
- широту и долготу.

При изменении контракта backend обновляйте DTO и функцию нормализации, а не размазывайте преобразования по компонентам.

## Локализация, стили и ресурсы

`LanguageProvider` предоставляет `useLanguage()` с языками `uk` и `en`. Украинский — исходный язык ключей; для английского используется словарь в `src/i18n.tsx`. Если перевода нет, функция возвращает исходную строку. Выбор сохраняется под ключом `homefu-language` в `localStorage`.

Глобальные токены дизайна определены в `src/tokens.css`: палитра, семантические цвета, шрифты, тени, радиусы и отступы. Общие правила находятся в `src/index.css` и `src/App.css`; стили экранов и компонентов обычно лежат рядом в соответствующем каталоге `components/`. Для новых стилей сначала используйте существующие CSS-переменные.

`index.html` подключает шрифты Inknut Antiqua, Nunito Sans и Inder с Google Fonts. Карта использует Leaflet и тайлы OpenStreetMap. Переключатель транспортного слоя содержит демонстрационный URL Thunderforest с заглушкой API-ключа и не заработает без отдельной конфигурации ключа.

## Проверки

Из `frontend/`:

```sh
npm test
npm run lint
npm run build
```

Тесты находятся рядом с проверяемой областью и покрывают API-клиент, фильтрацию/поиск, галерею, сохранённые объявления, форматирование цены и интеграцию приложения. При добавлении поведения обновляйте соответствующие тесты; для UI-сценариев используйте существующие Vitest и Testing Library.

## Правила разработки

1. Сначала ищите существующий компонент, API-клиент, hook и общий тип — не дублируйте ту же ответственность.
2. Сохраняйте границы: API и нормализация данных — в `src/api/`, UI — в `components/`, совместное состояние и переходы — в `App.tsx`, переиспользуемая React-логика — в `hooks/`.
3. Определяйте и используйте типы для DTO, props и состояния; не обходите проверку типов небезопасными приведениями.
4. Показывайте ошибки пользователю на экранах, инициирующих действие; отменяйте устаревшие загрузки через `AbortController`.
5. Для нового текста добавляйте ключ/перевод в `src/i18n.tsx`; сохраняйте существующий стиль компонентов и CSS-токены.
6. После функционального изменения запускайте адресные тесты, а перед завершением — `npm run build` и `npm run lint`, если изменение затрагивает код.

## Текущие ограничения интерфейса

- Бронирование и оплата сейчас являются интерфейсным сценарием: выбор полной или частичной оплаты и данные формы не отправляются в API. Кнопка оплаты валидирует часть введённых полей в браузере, показывает демонстрационное подтверждение и возвращает пользователя в каталог. Реального создания бронирования, авторизации карты или списания средств здесь нет.
- Длительность по умолчанию — пять ночей; в расчёте экранов бронирования/оплаты добавляется фиксированная плата `20`. Это клиентская демонстрационная формула, а не подтверждённая сумма серверного заказа.
- На экранах регистрации и входа через Google запрос отправляется в backend, однако клиентский callback не синхронизирует результат Google OAuth с `access_token` и состоянием аккаунта приложения.
- Маршруты не отражаются в URL, поэтому нельзя открыть отдельный экран приложения по прямой ссылке или сохранить его обновлением страницы.
- `ProfilePage.tsx` также содержит отдельные legacy-хелперы `fetchUserProfile`/`updateUserProfile` для `/api/profile`; основной экран профиля использует `/api/users/me/facts` через `src/api/users.ts`.
